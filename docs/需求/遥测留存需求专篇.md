# telemetry-store · 遥测留存需求专篇

- 版本：v1.0
- 日期：2026-02-14
- 定位：把**实时数据的留存**作为独立能力抽取为**单一交付模块**，供接口冻结、开发与验收直接使用
- 需求编号体系：`TLM-<域>-<序号>`；域：WRT（写入）/ QRY（查询）/ RPL（回放）/ GAP（补发）/ RET（保留）/ ADP（适配注入）/ OBS（可观测）/ NFR（非功能性）
- 口径：**只有两种状态：✅ 已完成 ｜ ⏳ 待完成**（当前功能条目全部为 ⏳，本专篇为立项文档，代码尚未开始）
- 分级用词：**MUST（必须，验收必查）/ SHOULD（应该，偏离需在决策记录说明）/ MAY（可选）**
- 技术栈口径：**服务端 C++17 + `nlohmann/json`**，接口以头文件冻结（与 `device-ingest` 同栈、同构建风格）
- 依据文档：
  - 模块划分 · 后续拆分方案（主仓 `docs/`，**不在本仓**）：§三 模块 3 `telemetry-store`、§四 仓库归属、§七 四条规则、§九 验收清单
  - 本仓 `README.md`（模块边界与职责已达成的 R0 结论）
  - `realtime-hub/protocol.md`（信封格式 `{type, data, ts}`：**本模块只依赖它的语法，不依赖它的实现**）
- 边界一句话：**它只回答"过去那段时间，这条流里到底发生了什么？"**

## 1. 定位与边界

### 1.1 它在链路里的位置

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│   ①  入口     │   │   ②  管道     │   │   ③  留存     │   │   ④  出口     │
│  把设备数据   │──▶│  把事件推给   │──▶│  把数据存下来 │──▶│  把数据画出来 │
│  变标准       │   │  所有客户端   │   │  可查可回放   │   │              │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
  device-ingest      realtime-hub      telemetry-store       map-2d
                     + ws-client        ← 本模块
```

### 1.2 它是什么 / 不是什么

**它是数据层模块**：只认"**带时间戳的流式数据**"。

| | `telemetry-store` | 业务数据库 |
|---|---|---|
| 存什么 | **带时间戳的流式数据** | 业务实体 |
| 数据形状 | **追加为主**，几乎不改不删 | 增删改查都有 |
| 主键 | **设备 ID + 时间** | 业务主键 |
| 生命周期 | 有**保留期**，到期清理 | 长期保存 |
| 谁能用 | **任何有实时流的系统** | 只有你的项目 |

### 1.3 范围边界（🚫 明确不做）

| 边界 | 内容 | 归谁 |
|---|---|---|
| 🚫 不做推送 | "现在有数据了，怎么送到每个人手上" | `realtime-hub` |
| 🚫 不做连接管理 | 谁连着、谁断了、什么时候断的 | `ws-client` / 部署层 |
| 🚫 不做业务查询 | "哪个任务完成了""这个目标评估如何" | 业务数据库 |
| 🚫 不做画图 | 画成地图、曲线、报表 | 出口模块（`map-2d` 等） |
| 🚫 不做字段语义 | 不认识 `lng` / `lat` / `rssi` 是什么意思，**不索引、不改写** | 上游模块与其契约 |
| 🚫 不做鉴权 | 谁能查哪段历史 | 部署层（反向代理 / 网关） |
| 🚫 不做集群 | 分片、复制、一致性协议 | 后续版本，本轮不涉及 |
| 🚫 不做投递保证修正 | hub 是 at-most-once，本模块**只如实记录收到的**，不伪造缺口 | — |

| 约束 | 取值 | 依据 |

## 2. 已确认的输入约束（需求评审结论）

| 项 | 结论 |
|---|---|
| 模块归属 | **独立仓**（数据层与"推"是两件事；见 `README.md` §为什么单独一个仓） |
| 技术栈 | **服务端 C++17**，头文件冻结接口，`nlohmann/json` 承载 `data`；CMake 可 `add_subdirectory` |
| 规模 | ≈ **1000 台设备 × 1 Hz × 200 B** ≈ **1000 条/s ≈ 200 KB/s** |
| 数据量 | ≈ **17 GB/天**（未压缩、无索引开销）→ 保留期必须可配置，否则只增不减 |
| 部署形态 | 单机进程内库（与宿主同进程）；跨机部署由宿主的采集进程调 `append` |
| 存储后端 | **不预设**。默认给一个**零依赖**实现（clone 下来就能跑）；生产可换 SQLite / 时序库 / 文件分段 |
| 落库触发 | **宿主装配点调用**（`onEvent → append`）。模块**不订阅**、不主动拉取任何上游 |
| 补发归属 | **补发是本模块的活**（`realtime-hub` 明确不管，见 `protocol.md` §11） |
| 接口冻结 | **R1 必须先做**，先行于一切实现 |
| 本轮不做 | 集群 / 加密 / 权限 / 业务查询 / 采样聚合算法（只做**取点**，不做**算指标**） |

### 2.1 五条贯穿全程的判定原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | **只记事实，不做解释** | 收到什么记什么；不推算、不补全、不修改 `data` 内容 |
| P2 | **不静默丢数据** | 任何丢弃（缓冲溢出、后端拒收、清理过期）**必须**有计数器与可读日志 |
| P3 | **缺口可见** | 记录带**单调递增序号**；序号不连续 = 有缺口，可查可告警，不假装完整 |
| P4 | **越界要明说** | 查询超限**报错**而不是静默截断；数据已被清理时**如实告知**覆盖范围 |
| P5 | **换后端不改模块** | 模块内**不出现任何 SQL / 连接串 / 表名**；一切存储细节在注入的后端里 |

## 3. 功能需求条目

### 3.1 写入（TLM-WRT）

> 一条"记录"= **一个时刻上的一次事件**：`{ deviceId, type, ts, data }`。不区分业务类型，不预设字段。

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TLM-WRT-01 | **MUST** 提供单条追加接口 `append(deviceId, type, ts, data)`，调用即返回，**不与存储后端同步**（不得因落盘慢而阻塞宿主线程） | 后端故意延迟 50 ms/批时，`append` 的 P95 返回时间仍 ≤ 1 ms | ⏳ |
| TLM-WRT-02 | **MUST** 提供批量追加接口 `appendBatch(vector<Record>)`（宿主已有整批数据时一次交进来） | 一次交 1000 条与逐条交 1000 条，落库结果完全一致 | ⏳ |
| TLM-WRT-03 | **MUST** 批量缓冲写：按**条数或时间**双阈值刷盘（默认 **1000 条 / 200 ms**），阈值可配置 | 1000 条/s 持续写入 10 分钟，后端收到的写入调用次数 ≤ 输入条数的 1/100 | ⏳ |
| TLM-WRT-04 | **MUST** 时间戳语义：`ts` 由**调用方传入**（事件产生时刻，epoch 毫秒）；模块**不自己打时间** | 同一事件在 `append` 前后被宿主记录的时间不一致时，查询结果以传入 `ts` 为准 | ⏳ |
| TLM-WRT-05 | **MUST** 记录序号：模块为每条记录打**进程内单调递增序号**，供缺口检测（P3） | 序号连续可查；人为丢弃一段记录后，缺口可被检出 | ⏳ |
| TLM-WRT-06 | **MUST** 缓冲有界：未刷盘缓冲上限可配置（默认 65536 条）；达到上限的行为是**可配置的**（阻塞等待 / 淘汰最旧 + 计数告警），**禁止无计数的静默丢弃** | 上限设为 100 条并灌入 10000 条：行为符合配置，且丢弃计数 = 实际丢弃条数 | ⏳ |
| TLM-WRT-07 | **MUST** 优雅停机：`flush()` 与析构时把缓冲全部交付后端；进程收到终止信号时宿主可调用 `flush()` 且 **5 s 内返回** | 写满缓冲后立即 `flush()`，重启进程查询，数据完整无缺 | ⏳ |
| TLM-WRT-08 | **MUST** 幂等/覆盖语义明确：相同 `(deviceId, ts, type)` 重复写入时，默认**后写覆盖先写**（同一时刻同一事件只留一份），不产生重复点 | 同一 `(deviceId, ts, type)` 写两次，`query` 只返回一条且内容为后写入的 | ⏳ |

### 3.2 查询（TLM-QRY）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TLM-QRY-01 | **MUST** 区间取数 `query(deviceId, fromTs, toTs)`，区间语义 **`[fromTs, toTs)` 左闭右开**，结果**按 `ts` 升序** | 造 0..999 毫秒数据，`query(100, 200)` 返回 100 条（含 100 不含 200） | ⏳ |
| TLM-QRY-02 | **MUST** 支持**单设备精确查询**（主键路径：设备 ID + 时间区间），这是最高频的查询形态 | 1000 台设备数据中查 1 台 1 小时，P95 ≤ 200 ms（见 TLM-NFR-03） | ⏳ |
| TLM-QRY-03 | **MUST** 支持**跨设备查询** `query(devices[], fromTs, toTs)`（"这段时间里所有设备发生了什么"），结果按 `ts` 升序、同 `ts` 按设备 ID 稳定排序 | 查 1000 台设备 1 分钟窗口，返回条数与写入条数一致，排序稳定可复现 | ⏳ |
| TLM-QRY-04 | **MUST** 分页/游标：单次查询返回条数上限可配置（默认 **10000**），超出时返回**续查游标**；**禁止静默截断**（P4） | 2 万条数据一次查询：返回 1 万条 + 游标，用游标续查得到剩余 1 万条，无重复无遗漏 | ⏳ |
| TLM-QRY-05 | **MUST** 结果附带**覆盖范围元信息**：实际返回的 `[最早 ts, 最晚 ts]`、条数、是否被清理过（`truncatedByRetention`）、是否可能不完整（`partial`） | 数据被清理后查同一区间，`truncatedByRetention=true` 且最早 `ts` 等于保留边界 | ⏳ |

### 3.3 回放（TLM-RPL）

> **回放 = 一次区间查询 + 按输出契约打包。** 数据在**服务端 / 宿主**取出，**按真实时间间隔播放是出口模块（前端）的事**——本模块不写定时器、不做动画。

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TLM-RPL-01 | **MUST** 输出**时间轴格式**（timeline）：有序样本序列 + 起止时刻 + 总时长，**直接可喂给回放组件** | `examples/replay_demo` 取出 10 分钟数据，输出的 timeline 能被按 `ts` 差播放，无需再转换 | ⏳ |
| TLM-RPL-02 | **MUST** timeline 与 `query` **同源同语义**：`[from, to)` 左闭右开、升序、同样遵守 TLM-QRY-04 的上限与游标 | 同一区间 `query` 与 `replay` 返回的样本集合完全相同 | ⏳ |
| TLM-RPL-03 | **MUST** 支持单设备回放与多设备回放；多设备时按 `ts` 归并为**一条统一时间轴** | 3 台设备交错上报，timeline 中样本按 `ts` 全局有序 | ⏳ |
| TLM-RPL-04 | **SHOULD** 支持**稀疏化**参数（`everyNth` 取每第 N 条 / `minIntervalMs` 最小间隔），用于长时间跨度的低精度回放；稀疏化**必须**在结果里标注（`sampled: true, sampleStep: N`） | 请求 10 万点、步长 10：返回 1 万点且 `sampled=true`；不传参数时行为与 TLM-RPL-02 完全一致 | ⏳ |

### 3.4 补发（TLM-GAP）

> 这是本模块与 `realtime-hub` 的**分界线**：hub 管"在场的人"，留存层管"发生过的事"。
> 客户端重连后**自己去查**断线期间发生了什么（`protocol.md` §7.1 / §11）。

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TLM-GAP-01 | **MUST** 提供续查接口 `since(deviceId, lastSeenTs)` → 返回 **`ts > lastSeenTs`** 的记录（**严格大于**，避免与客户端已有数据重复） | 客户端已有 `ts=1000` 的点，`since(...,1000)` **不含** 1000，只返回 1001 起的新点 | ⏳ |
| TLM-GAP-02 | **MUST** 支持多设备补发 `since(devices[], lastSeenTs)`，以及**每设备各自水位** `since(map<deviceId, ts>)` | 3 台设备水位不同，各自只收到自己水位之后的数据 | ⏳ |
| TLM-GAP-03 | **MUST** 补发遵守条数上限与游标（复用 TLM-QRY-04）：缺口很大时**分批续查**，不一次性返回全量 | 补发 5 万条缺口：分 5 批返回，游标续查无缝衔接 | ⏳ |
| TLM-GAP-04 | **MUST** 支持**缺口识别** `gaps(fromTs, toTs)` → 返回每个设备的**未覆盖时间区间列表**，供客户端如实提示"这段时间数据缺失"，而不是假装连续 | 人为关停写入 5 分钟，`gaps()` 能报出这 5 分钟区间 | ⏳ |
| TLM-GAP-05 | **MUST NOT** 由本模块主动推送补发数据到客户端（P5 边界）：补发是**查询**，客户端重连后自己发起 | 模块内不存在任何向连接写数据的路径（代码审查项） | ⏳ |

### 3.5 保留（TLM-RET）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TLM-RET-01 | **MUST** 可配置保留期：默认保留 **7 天**（≈120 GB，见 §2），可按 `type` 覆盖（如 `link.quality` 只留 1 天） | 改配置为 1 小时后，1 小时前的数据被清理，之后的完整保留 | ⏳ |
| TLM-RET-02 | **MUST** 清理**不阻塞**写入与查询（后台维护节奏，无写入停顿） | 清理 100 万条期间，`append` P95 与 `query` P95 不劣化超过 20% | ⏳ |
| TLM-RET-03 | **MUST** 清理可观测：记录已清理条数、最早已清理 `ts`、上次清理时刻；清理**失败可读可查** | 查看状态接口能读到上述三项，且与实际清理结果一致 | ⏳ |
| TLM-RET-04 | **MUST** 后端能力诚实：注入的后端若**不支持删除**（如追加型文件分段），`purge` 返回"不支持"而非假装成功；此时保留策略降级为"只标记、不删除"并可观测 | 用一个 `canPurge()==false` 的后端：调用清理返回不支持，模块不报错、不谎报 | ⏳ |
| TLM-RET-05 | **SHOULD** 支持容量上限（按记录数或字节数）作为保留期的补充手段，超限按最旧优先淘汰并计数 | 容量设为 1 万条，灌 2 万条：剩余 1 万条且淘汰计数 = 1 万 | ⏳ |

### 3.6 适配注入（TLM-ADP）

> **这一域是模块能独立交付的全部秘密**：模块对外只有接口，宿主需要定制的地方全部注入。

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TLM-ADP-01 | **MUST** 存储后端通过反向接口 `IStorageBackend` 注入（追加 / 区间读 / 清理 / 能力声明 / 高水位）；模块内**零 SQL、零连接串、零表名** | 换一个后端实现（内存 → 文件 → SQLite）只改宿主装配代码，模块源码零改动 | ⏳ |
| TLM-ADP-02 | **MUST** 时间源通过 `IClock` 注入，测试与回放可替换；模块内部取"现在"只经此接口 | 用假时钟把"现在"设为固定值，保留清理行为可被确定性测试 | ⏳ |
| TLM-ADP-03 | **MUST** 保留策略通过 `IRetentionPolicy` 注入（留多久 / 什么时候清 / 容量上限），模块不写死默认以外的任何业务口径 | 换一种策略实现（按 type 分别设期）无需改模块 | ⏳ |
| TLM-ADP-04 | **MUST** 落库触发由**宿主装配点**负责（`onEvent → append`）；模块**不订阅**上游、不依赖 `device-ingest` / `realtime-hub`。MAY 提供一个**纯函数** `fromEnvelope(json)` 把标准信封转成记录（只依赖信封语法） | 模块可以只被一个不存在的上游驱动：`examples` 里手工 `append` 也能跑通全流程 | ⏳ |

### 3.7 可观测（TLM-OBS）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TLM-OBS-01 | **MUST** 提供状态快照 `status()`（JSON）：已收条数 / 已落库条数 / 缓冲深度 / 丢弃计数 / 已清理条数 / 后端写入耗时 / 后端写入失败次数 | 上述字段齐全，数值与实际灌入量对得上 | ⏳ |

## 4. 交付验收清单

交付前必须逐条回答"是"（沿用拆分方案 §九）：

- [ ] **独立构建**：空环境 clone 下来，一条命令编译通过，**不需要任何外部服务**
- [ ] **独立运行**：`examples/` 里最小示例，不接宿主也能跑出"写入 → 查询 → 回放 → 补发"
- [ ] **独立测试**：自带测试，不依赖宿主的数据库和配置
- [ ] **接口稳定**：对外只有 `include/telemetry_store/` 下少数几个头文件，且已写进文档
- [ ] **反向接口**：`IStorageBackend` / `IClock` / `IRetentionPolicy` / `ILogSink` 全部注入，无写死实现
- [ ] **零业务依赖**：源码里搜不到"任务 / 方案 / 目标 / 场景 / 阶段 / 编组 / 评估"
- [ ] **零跨仓 import**：不 import 其它任何模块的内部
- [ ] **有配套工具**：`tools/` 下至少一个造流式数据 / 压写入频率的工具
- [ ] **能一句话说清**：**"把实时流存下来，能查、能回放、能补发。"**（不需要提你的项目）

## 5. 一句话

> **它只回答"刚才发生了什么"。**
> 进来的是一份带时间戳的数据，出去的是一段可以查、可以回放、可以补发的时间轴。
> 它不认识设备，不认识地图，也不认识你项目里的任何一个业务词。
