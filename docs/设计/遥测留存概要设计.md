# telemetry-store · 概要设计说明书（简略）

- 版本：v1.0
- 日期：2026-02-14
- 定位：模块的**结构与接口冻结稿**。写完本文档即可开工——**本文档不打补丁，只冻结**
- 需求依据：[遥测留存需求专篇](../需求/遥测留存需求专篇.md)（`TLM-*` 编号，本文逐条可追溯）
- 技术栈：**C++17** · `nlohmann/json` · CMake（可 `add_subdirectory`）· 默认零外部依赖
- 公开面：`include/telemetry_store/` 下 **6 个头文件**（2 个数据结构 + 3 个反向接口 + 1 个门面）
- 一句话：**把实时流存下来，能查、能回放、能补发。**

## 1. 架构总览

```
                        宿主（业务装配点）——只有这一层懂业务
                                  │
                     onEvent(ev) → store.append(...)          ← 唯一的接入方式（TLM-ADP-04）
                                  ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  telemetry-store                                                        │
│                                                                         │
│  ① 门面 Store            存 / 查 / 回放 / 补发 / 状态（对外唯一入口）      │
│         │                                                               │
│  ② 写入路径                                                              │
│     rec 构造（打 seq）→ 有界环形缓冲 → 按（1000 条 / 200 ms）成批刷出     │
│         │                                              ↑ 由调用驱动      │
│  ③ 查询路径                                                              │
│     区间裁剪 → 后端读 → 去重(last-wins) → 排序 → 游标 + 覆盖元信息        │
│         │                                                               │
│  ④ 保留路径（独立维护线程）                                              │
│     读 IRetentionPolicy → 时间/容量裁剪 → canPurge 判定 → 记账           │
│         │                                                               │
│  ⑤ 反向接口（宿主注入 · 模块内不出现任何具体存储）                         │
│     IStorageBackend   IClock   IRetentionPolicy   ILogSink              │
└─────────────────────────────────────────────────────────────────────────┘
                                  │  只收带时间戳的流 · 不认识字段含义
                                  ▼
                 查询结果 / timeline ──▶ 出口模块（回放组件、曲线、报告）
```

**五条不可动摇的结构性事实**

| # | 事实 | 由来 |
|---|---|---|
| 1 | 数据**只从 `append` 进**（宿主调用） | 模块不订阅、不拉取，零上游依赖（TLM-ADP-04） |
| 2 | 模块内**没有 SQL / 连接串 / 表名** | 存储细节全在注入的后端里（TLM-ADP-01 / P5） |
| 3 | 时间**不入库为"现在"**：`ts` 由调用方给，`IClock` 只用于保留与统计 | TLM-WRT-04 / TLM-ADP-02 |
| 4 | 回放**不播**，只出时间轴 | 播放节奏属出口模块（TLM-RPL-01） |
| 5 | 补发是**查询**，不是推送 | `protocol.md` §11 的分界（TLM-GAP-05） |

## 2. 数据模型

### 2.1 记录：一行 = 一个时刻上的一次事件

```cpp
struct Record {
    std::string    deviceId;   // 设备标识（主键前半）
    std::string    type;       // 事件名，形如 uav.pos / link.quality（信封 type 原样）
    std::int64_t   ts   = 0;   // 事件产生时刻，epoch 毫秒（主键后半）
    nlohmann::json data;       // 事件负载，**原样透传**，模块不看、不改、不索引
    std::uint64_t  seq  = 0;   // 进程内单调递增序号，供缺口检测（TLM-WRT-05 / P3）
};
```

**逻辑主键 = `(deviceId, ts, type)`**；`seq` 是**诊断信息，不是主键**——它随进程重启归零，只用于"这批数据有没有缺口"。

### 2.2 物理存储不是模块的事

模块**只定义逻辑行**。物理形态由 `IStorageBackend` 决定：

| 后端 | 物理形态 | 默认实现 |
|---|---|---|
| 内存 | 环形缓冲 | ✅ L1（零依赖，clone 即跑） |
| 文件分段 | 按时间切段的追加文件 + 段内稀疏索引 | ✅ L2（TTL-NFR-07 仍零外部依赖） |
| SQLite / 时序库 | 由宿主实现 | ❌ 模块不提供（避免把选型焊进来） |

### 2.3 为什么 `data` 是 JSON 而不是 `vector<double>`

上游事件本来就是 JSON（`protocol.md` §1）。**留成 JSON 才能"不认识业务"**：不认识 `lng`，也不认识 `rssi`，只当它是黑盒负载。代价是存储比二进制胖——**这是刻意的取舍**，换回来的是"任何人拿来就能用"。

## 3. 对外接口（冻结）

### 3.1 公开头文件清单

```
include/telemetry_store/
├─ record.h      数据结构：Record / Query / QueryResult / Timeline / Gap / Status
├─ backend.h     IStorageBackend   （存哪里——注入）
├─ policy.h      IRetentionPolicy  （留多久——注入）
├─ clock.h       IClock            （时间来源——注入）
├─ log_sink.h    ILogSink          （日志出口——注入，可空）
└─ store.h       门面 Store        ★ 宿主只认识这一个
```

**规则：除 `store.h` 外，其余头文件都是"宿主实现侧"的头文件。** 业务代码只 `#include <telemetry_store/store.h>`。

### 3.2 门面 `Store`

```cpp
namespace telemetry_store {

struct StoreOptions {
    FlushPolicy           flush;                     // 默认：1000 条 / 200 ms
    std::size_t           bufferCapacity = 65536;    // 未刷盘缓冲上限（条）
    BufferFullPolicy      onFull = BufferFullPolicy::DropOldest;  // 或 Block
    std::size_t           maxRowsPerQuery = 10000;   // 单次查询上限（TLM-QRY-04）
    std::int64_t          sweepIntervalMs = 60000;   // 保留巡检周期
    std::int64_t          nominalPeriodMs = 1000;    // 名义上报周期，gaps() 默认阈值 3×（TLM-GAP-04）
    bool                  enableSweeper  = true;     // 测试可关掉维护线程
};

class Store {
public:
    Store(StoreOptions opt,
          IStorageBackend& backend,        // 必需（引用：生命周期由宿主保证）
          IClock&          clock,          // 必需
          IRetentionPolicy& policy,        // 必需
          ILogSink*        log = nullptr); // 可空
    ~Store();                              // 析构等价于 flush()（TLM-WRT-07）

    Store(const Store&)            = delete;
    Store& operator=(const Store&) = delete;

    // ── 写入（非阻塞、不抛异常；失败只记账，见 §6.2）────────────────
    void append(const Record& rec);                       // TLM-WRT-01
    void append(std::string_view deviceId, std::string_view type,
                std::int64_t ts, nlohmann::json data);    // 便捷重载
    void appendBatch(const std::vector<Record>& recs);     // TLM-WRT-02
    void flush();                                          // 交付全部缓冲；5s 内返回（TLM-WRT-07）

    // ── 查询（区间一律 [from, to) 左闭右开；结果 ts 升序）───────────
    QueryResult query(const Query& q) const;               // TLM-QRY-01/02/03
    QueryResult queryPage(const Query& q, const Cursor& c) const;  // 分页续查（TLM-QRY-04）

    // ── 回放 / 补发 ───────────────────────────────────────────────
    Timeline since(const SinceRequest& req) const;         // ts > lastSeenTs（TLM-GAP-01/02/03）
    Timeline replay(const ReplayRequest& req) const;       // 时间轴（TLM-RPL-01..04）
    std::vector<Gap> gaps(std::int64_t fromTs, std::int64_t toTs,
                          std::int64_t maxGapMs = 0) const; // 0 = 用 nominalPeriodMs×3（TLM-GAP-04）

    // ── 保留 / 状态 ───────────────────────────────────────────────
    RetentionReport sweep();                               // 立即巡检一次（TLM-RET-01..05）
    Status status() const;                                 // 可观测快照（TLM-OBS-01）

    // ── 纯函数：标准信封 → 记录（不 import 任何上游代码，TLM-ADP-04）──
    static bool fromEnvelope(const nlohmann::json& envelope, Record& out);
    // 信封形状 { "type": ..., "data": {...}, "ts": ... }；缺字段/类型不符 → false
};

}  // namespace telemetry_store
```

### 3.3 请求/结果结构

```cpp
struct Query {
    std::vector<std::string> devices;      // 空 = 全部设备（TLM-QRY-03）
    std::vector<std::string> types;        // 空 = 全部类型
    std::int64_t fromTs = 0;               // 含
    std::int64_t toTs   = 0;               // 不含
    std::size_t  limit  = 0;               // 0 = 用 StoreOptions::maxRowsPerQuery
};

struct Cursor {                            // 上次结果末尾之后的位置；非法/为空 = 从头
    std::int64_t  ts       = 0;
    std::string   deviceId;
    std::string   type;
    bool          valid    = false;
};

struct QueryResult {
    std::vector<Record> rows;              // ts 升序；同 ts 按 deviceId 稳定排序
    bool         hasMore = false;          // true 时用 cursor 续查
    Cursor       cursor;
    std::int64_t coveredFromTs = 0;        // 实际返回的最早/最晚 ts（TLM-QRY-05）
    std::int64_t coveredToTs   = 0;
    bool         truncatedByRetention = false;  // 查询区间早于保留边界
    bool         partial = false;               // 命中了缓冲未刷盘 / 序号缺口 → 可能不完整
};

struct Timeline {                          // 回放 / 补发的共同输出（TLM-RPL-01/02）
    std::int64_t fromTs = 0, toTs = 0;
    std::int64_t durationMs = 0;
    std::vector<Record> samples;           // 全局 ts 升序（多设备时是归并的一条时间轴）
    bool         sampled = false;          // 稀疏化过（TLM-RPL-04）
    std::size_t  sampleStep = 1;           // everyNth 的实际步长
    bool         hasMore = false;
    Cursor       cursor;
    bool         truncatedByRetention = false;
};

struct ReplayRequest {
    Query       q;                         // 复用查询条件（同源同语义）
    std::string deviceId;                  // 单设备回放便捷字段（与 q.devices 二选一）
    std::size_t everyNth    = 1;           // 每第 N 条
    std::int64_t minIntervalMs = 0;        // 最小间隔；与 everyNth 同时给出时取更稀疏者
};
```

**`ReplayRequest` 里没有 `speed` 字段**——因为**回放速度是播放器的事**。模块只保证样本按 `ts` 有序且带真实时刻，出口模块按 `ts` 差自行决定"1 秒数据播几秒"。

### 3.4 状态快照

```cpp
struct Status {                            // 全部字段可 JSON 序列化（TLM-OBS-01/02）
    std::uint64_t appended = 0, persisted = 0, buffered = 0;
    std::uint64_t droppedByOverflow = 0;   // 缓冲溢出丢弃（P2：必有计数）
    std::uint64_t backendWriteFailures = 0;
    std::uint64_t rejectedByLimit = 0;     // 查询超限拒绝
    std::uint64_t purgeFailures = 0, purgedRows = 0;
    std::int64_t  earliestPurgedTs = 0;
    double        lastWriteMs = 0, avgWriteMs = 0;
    std::uint64_t seqFirst = 0, seqLast = 0;  // 差值 ≠ appended 即存在缺口（P3）
    std::string   thresholdState;          // ok | degraded（后端连续失败）
    nlohmann::json toJson() const;
};
```

### 3.5 反向接口

```cpp
// ── backend.h：存哪里 ──────────────────────────────────────────────
class IStorageBackend {
public:
    virtual ~IStorageBackend() = default;

    /// 成批追加（TLM-WRT-03 的落点）。返回 false = 已拒收，调用方保留数据下轮重试。
    virtual bool append(std::span<const Record> recs) = 0;

    /// 区间读：[fromTs, toTs)；devices / types 为空表示不过滤；
    /// 最多返回 limit 条；beginAfter 用于续查（nullptr = 从头）。
    /// 后端 SHOULD 按 ts 升序返回；模块会自行排序，不依赖此保证。
    virtual QueryResult read(const Query& q, const Cursor* beginAfter) = 0;

    /// 删除 ts < cutoffTs 的数据（清理由模块裁决，执行由后端做）。
    virtual bool purge(std::int64_t cutoffTs) = 0;
    virtual bool canPurge() const = 0;        // false → 保留降级为"只标记"（TLM-RET-04）

    /// 已达标数据的最早 ts 高水位；无数据返回 0。用于 truncatedByRetention 判定。
    virtual std::int64_t earliestRetainedTs() const = 0;
    virtual std::size_t  approxRows() const = 0;      // 容量策略用（TLM-RET-05），可为估算
    virtual const char*  name() const = 0;            // 诊断用，如 "memory" / "segfile"
};

// ── policy.h ───────────────────────────────────────────────────────
class IRetentionPolicy {
public:
    virtual ~IRetentionPolicy() = default;
    virtual std::int64_t ttlMs(const std::string& type) const = 0;  // 按类型覆盖（TLM-RET-01）
    virtual std::size_t  maxRows() const = 0;                       // 0 = 不限（TLM-RET-05）
    virtual std::size_t  maxBytes() const = 0;                      // 0 = 不限
};

// ── clock.h ────────────────────────────────────────────────────────
class IClock {
public:
    virtual ~IClock() = default;
    virtual std::int64_t nowMs() const = 0;                         // 只用于保留/统计（TLM-ADP-02）
};

// ── log_sink.h（与 device-ingest 同风格，可空）─────────────────────
class ILogSink {
public:
    virtual ~ILogSink() = default;
    /// category ∈ { wrt, qry, rpl, gap, ret, obs }
    virtual void log(const std::string& category, const nlohmann::json& payload) = 0;
};
```

**接口设计的三条硬规矩**

1. **`append` 取 `span`**：批量缓冲的全部意义就在这里——1000 条/s 变成 ~1 次/s 后端调用（TLM-WRT-03）。
2. **`read` 收 `Query` + `Cursor`**：模块与后端对"分页"用同一种话，避免模块自己拉全量再截断。
3. **能力要声明**（`canPurge`）：**后端不会做的事，模块不许假装它会做**（TLM-RET-04 / P4）。

## 4. 关键机制

### 4.1 写入路径（TLM-WRT-01/03/06/07）

```
append(rec)
  ├─ 补 seq（单锁临界区，保证单调）        ← 序号即缺口证据（P3）
  ├─ 入有界环形缓冲
  │    └─ 满？（先想办法腾空间，再考虑丢）
  │         ├─ onFull = Block（可选）    → 在锁上等到腾出空间（2 s 兜底，见下）
  │         ├─ 先 flushLocked()          → 后端健在时**一条都不丢**（这是常态）
  │         └─ 仍满 → 淘汰最旧 + droppedByOverflow++ + 计数日志
  │              （DropOldest 只在**后端持续拒收**时才真正丢数据，见 D17-b）
  └─ 判定 FlushPolicy（1000 条 或 200 ms 到）
       └─ 成立 → 取走整批 → backend.append(RecordBatch)  ← 与调用线程同步，不另开写线程
```

> `Block` 策略带 **2 s 兜底**：`append` 不允许无限期挂住宿主线程，
> 超时后按 DropOldest 处理并计数——"绝不静默丢"和"绝不无限阻塞"两条都要成立。

**为什么"由调用驱动刷盘"而不是"独立写线程"（决策 D6）**

| 方案 | 代价 |
|---|---|
| **调用驱动**（选定） | `append` 的 P95 会偶尔包含一次后端写入；**但模块没有线程生命周期问题**，测试可完全确定性（手动 `flush()`） |
| 独立写线程 | 需要跨线程队列 + 唤醒/退出协议 + 空闲轮询；对 200 KB/s 的规模，收益不抵复杂度 |

约束：因此 `append` 的延迟承诺是 **P95 ≤ 1 ms**（绝大多数调用不触发刷盘），**不是 P100**——触发刷盘的那一次会等于一次后端写入耗时。这条**必须写进文档**，否则使用者会误以为 `append` 恒定快。

### 4.2 去重：写在读路径（决策 D7）

同一 `(deviceId, ts, type)` 可能出现多份（宿主重复投递、重连回溯、后端不支持 upsert）。

```
读路径：按 (deviceId, ts, type) 折叠 → 保留 seq 最大的一条（后写胜）   → 语义等价于 TLM-WRT-08
```

**为什么不要求后端 upsert**：upsert 会把"必须有唯一索引 / 必须支持更新"变成对后端的硬要求——那正好是**把选型焊进模块**。写在读路径，后端只做追加，**任何后端都能满足**。

### 4.3 分页游标：`(ts, deviceId, type)` 三元组（决策 D8 / TLM-QRY-04）

```
cursor = 上次返回的最后一条的 (ts, deviceId, type)
下一次：返回所有严格大于该三元组的记录（ts 升序，同 ts 内按 deviceId/type 排）
```

**排序是全序，所以续查不重不漏**。`limit` 用尽时 `hasMore=true` 并回传 `cursor`；**绝不静默截断**（P4）。

### 4.4 补发语义（TLM-GAP-01..04）

```
客户端断线 → 重连 → 它手上有水位 lastSeenTs（本地最后一条的 ts）
                    ↓ 自己去查（不是等推送，TLM-GAP-05）
   since(lastSeenTs) → 严格返回 ts > lastSeenTs 的记录，分页给出
                    ↓ 缺口太大？
   gaps(from, to)    → 每设备未覆盖区间列表，客户端如实提示"这段时间没有数据"
```

**`gaps()` 的判定口径（决策 D9，标注为 SHOULD）**：相邻两条记录间隔 `> maxGapMs`（默认 `nominalPeriodMs × 3`）即视为一段缺口。这是**阈值法**，不是语义判断——真正的失联判定属设备健康域（`device-ingest` 的 `HLT`），**本模块不重复实现**，只提供可配置阈值与如实输出。

### 4.5 保留与清理（TLM-RET-01..05）

```
独立维护线程（每 sweepIntervalMs，默认 60 s）
   ├─ 读 IRetentionPolicy.ttlMs(type) → 计算最小 cutoff 与各类型 cutoff
   ├─ backend.canPurge()?
   │     ├─ false → 记录 retentionUnsupported = true，降级为"只标记"，不再重试（不谎报）
   │     └─ true  → backend.purge(cutoff) → purgedRows / earliestPurgedTs 记账
   ├─ 容量策略：approxRows() 或 maxBytes 超限 → 追加一次 purge（最旧优先）
   └─ 清理失败 → purgeFailures++ + 可读日志（P2），下轮继续
```

**清理绝不阻塞写入**：维护线程只调后端，不持写入缓冲的锁超过取批的那一瞬（TLM-RET-02）。

### 4.6 边界条件（**出错时才见真章的地方**）

| 情况 | 处置 | 依据 |
|---|---|---|
| `toTs <= fromTs` | 返回空结果 + `partial=false`，不报错、不扫全库 | — |
| 单次结果超 `limit` | 截断 + `hasMore=true` + 游标（**不是拒绝**） | TLM-QRY-04 |
| 请求的 `limit` 本身超上限 | `rejected=true` + `rejectReason` + 空结果 + `rejectedByLimit++`；**不许悄悄只给一部分** | TLM-OBS-02 / P4 |
| 查询落在缓冲未刷盘区间 | 结果照常返回（**先刷一次**再查，保证"刚写的能查到"），`partial` 在刷盘失败时为 true | TLM-QRY-05 |
| 后端 `append` 返回 false | 数据**留在缓冲**下轮重试；连续失败 → `thresholdState=degraded` + 计数 | TLM-OBS-02 |
| 后端 `append` 抛异常 | 与返回 false 同处置（模块边界内捕获，绝不让异常穿到宿主） | TLM-OBS-02 |
| `ts` 为 0 / 负数 | 接受并如实存储（时间戳由调用方负责），不打当前时间兜底 | TLM-WRT-04 |
| 乱序到达（设备时钟回拨） | 照原样存储；查询结果仍按 `ts` 升序，**模块不修正时间** | P1 |
| 进程被 `kill -9` | 未刷盘缓冲丢失，**如实反映为 seq 缺口**，不谎报完整 | TLM-NFR-06 |
| 同一后端实例被多个 `Store` 使用 | **不允许**：一个 `Store` 独占一个后端实例（写入缓冲的独占性依赖此约定） | — |
| 后端不支持删除 | 保留降级 + 可观测，不报错、不假装成功 | TLM-RET-04 |

## 5. 并发模型（TLM-NFR-05）

```
线程                            触达的东西                          同步
────────────────────────────── ────────────────────────────────── ────────────────────
宿主写入线程（1..N）              append / flush                       Store 内部单锁
宿主查询线程（1..M）              query / since / replay / gaps        同一把锁（临界区极短）
模块维护线程（1，L3 起）           sweep → backend.*                   Store 内部单锁
────────────────────────────── ────────────────────────────────── ────────────────────
```

**约定（写进 `store.h` 注释）**

1. `Store` 的所有公开方法**线程安全**，可被多线程并发调用。
2. **`IStorageBackend` 实现必须线程安全**（模块可能从写入线程与维护线程同时调用它）——这是对实现方的硬要求，不是建议。
3. 锁粒度：取批/入队/游标记账在锁内，**后端调用在锁外**（避免慢后端把查询也堵住）。
   > 例外：`flush()` 为保"返回即已交付"的语义，后端调用在锁内完成。
4. 状态计数一律 `std::atomic`，`status()` **不加锁**即可读（它被调用得比查询频繁得多）。

### 6.3 错误处理口径

- **不使用异常跨越模块边界**：`append` / `flush` / `sweep` 不抛；后端抛出的异常在边界处被捕获并转成计数（§4.6）。
- **查询不抛业务错**：非法区间 → 空结果；超限 → 截断 + 游标。**"数据没了"和"查询写错了"必须能在结果里区分**（`partial` / `truncatedByRetention`）。

## 8. 决策记录（本文档的冻结项）

| # | 决策 | 取舍 | 状态 |
|---|---|---|---|
| D1 | **`Record` 只带 5 个字段，`data` 为原始 JSON、不索引不改写** | 换来"不认识业务"，代价是存储效率 | 冻结 |
| D2 | **存储后端 = 反向接口 + 两个零依赖默认实现**（L1 内存 / L2 文件分段） | 换来"换后端不改模块"；SQLite / 时序库留给宿主 | 冻结 |
| D3 | **`ts` 由调用方传入，模块不自己打时间** | 事件时刻的唯一真相在产生侧；避免"存储时刻"污染语义 | 冻结 |
| D4 | **记录带 `seq`，缺口可检出** | 崩溃丢未刷盘数据是允许的，**假装完整是不允许的** | 冻结 |
| D5 | **查询区间一律 `[from, to)`，结果 `ts` 升序** | 半开区间避免相邻查询重复 | 冻结 |
| D6 | **刷盘由调用驱动（1000 条 / 200 ms 双阈值），不设独立写线程** | 无线程生命周期复杂度；代价是 `append` 偶发包含一次后端写入（P95 承诺） | 冻结 |
| D7 | **去重写在读路径（last-wins），不要求后端 upsert** | 任何后端都能满足，不把索引/更新能力变成硬要求 | 冻结 |
| D8 | **游标 = `(ts, deviceId, type)` 三元组全序续查** | 不重不漏；后端只需支持"大于某位置" | 冻结 |
| D9 | **`gaps()` 用阈值法（默认 3× 名义周期），不做失联语义判定** | 不越界实现设备健康域的能力 | 冻结（阈值为 SHOULD 级） |
| D10 | **保留默认 7 天（≈120 GB）+ 按 type 覆盖 + 60 s 巡检** | 与 §2 规模口径自洽 | 冻结 |
| D11 | **不提供单例**（与 `device-ingest::Gateway` 不同） | 本模块无进程级共享状态，宿主需要几个就建几个 | 冻结 |
| D12 | **回放不含 `speed`，只出时间轴** | 播放节奏是出口模块的自由 | 冻结 |
| D13 | `maxRowsPerQuery` 默认 10000、`bufferCapacity` 默认 65536 | 初始口径，压测后调整 | **待确认** |
| D14 | `query` 延迟 P95 ≤ 200 ms（单设备 1 小时区间） | 需 L2 后端实测后回填 | **待确认** |
| D15 | `SegmentFileBackend` 的段切分粒度与段内索引形态 | **已定**（见下） | 冻结 |

### D15 定稿：段文件后端（实现期确定）

| 项 | 取值 | 理由 |
|---|---|---|
| 段文件命名 | `<起始ts 补零19位>-<序号6位>.seg` | **字典序 = 时间序**，装载已有段时按文件名排序即正确顺序 |
| 段容量 | `maxRowsPerSegment`，默认 65536 行 | 够大（减少段数）又够小（清理能整段删） |
| 段内格式 | 每条记录一行 JSON；`#idx ` 开头的行是**稀疏索引** | 一行一条 = 崩溃时最多坏最后一行，坏行跳过不影响整段（P2） |
| 索引粒度 | `indexEvery`，默认 1024 行 | 查询时二分跳到区间起点，不必反序列化前面几十万条 |
| 清理方式 | 整段删除；**只有跨越边界那一段**重写（临时文件 + 原子 rename） | 这正是"分段"最划算的地方（TLM-RET-04） |

> **实现期抓到的坑（写进决策，防止后人重犯）**：段读缓存一开始在命中时用 `move` 把
> `CacheEntry::rows` 掏空，于是**第一次查询正常、第二次查同一段返回空**——一个只在
> "同一段被读第二次"时才发作的 bug，而且伪装成"游标续查没数据"。
> 缓存命中必须**拷贝**出内容，不能 move。（由 `tests/manual_segfile_check.cc` 抓出）

### D16 定稿：两个只在"特定用法"下发作的 bug（实现期抓出，已修）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| B1 | **一稀疏化回放就返回 0 条**：`replay(everyNth=5)` 拿不到任何样本，但 `everyNth=1` 正常 | 回放为了"抽 1 条要多取 N 条候选"，把 `q.limit` 乘上了 `everyNth`（10000×5=50000）——正好撞上"请求超上限即拒绝"，于是整次查询被挡掉 | 回放**不再放大 `q.limit`**：候选数量由 `fetch` 的扫描上限（`maxScannedPerQuery`，默认 `maxRowsPerQuery×10`）自然约束；采样后超过 `baseLimit` 才截断并置 `hasMore` |
| B2 | **多设备查询永远报 0 段缺口**：`gaps()` 对单设备正确，传多台设备就什么都不报 | 缺口判定比较的是**相邻两行**；多设备交错上报时相邻两行几乎总是不同设备，于是 `r.deviceId != curDev` 一路重置，缺口全被漏掉 | **按设备分组**比较：用 `unordered_map<deviceId, 上一条>` 维护每设备自己的水位；输出再按 `(fromTs, deviceId)` 稳定排序 |
| B5 | **大区间 `gaps()` 静默漏报缺口**：窗口内约 2 万条、缺口落在后段时报"0 段"，调用方从 `vector<Gap>` 上完全看不出被截断 | `gaps` 内部 `q.limit=0`，而 `fetch` 把 0 解释成"用默认页大小 `maxRowsPerQuery`（10000）"，于是取数被截断，缺口恰好在被截掉的后半段 | `gaps` 改用 **ScanOnly** 内部口径取数（不受调用方页上限约束，只受 `maxScannedPerQuery` 约束）；真被扫描上限截断时记 `scanTruncated` 日志，**不假装分析过全区间** |

**这几个 bug 的共性值得记住**：它们都不在主路径上（一个是采样、一个是多设备、一个是超大区间），
单设备 / 不采样 / 小区间的测试全绿，**只有把功能组合起来用才暴露**。
所以示例程序不是装饰——`example_replay` 一跑就把 B1/B2 抓出来了，B5 由 `tools` 作者复现发现。

### D17 定稿：`partial` 的判定时机 · 容量淘汰计数 · `DropOldest` 的真实可达性

**B3 — `partial` 永远为 false（实现期抓出，已修）**

`fetch` 原来在 `flushLocked()` **之后**才快照 `backendWriteFailures_`，于是"查询前那次刷盘的失败"被吃掉，
`partial` 恒为 false —— 一个"越失败越说自己没问题"的错。**修法：快照移到 flush 之前。**

**B4 — 序号缺口没反映到 `partial`（实现期抓出，已修）**

`record.h` 把"序号缺口"列为 `partial` 的成因，但实现只在"写入失败/扫描截断"时置位。
**修法：一旦发生过缓冲溢出丢弃（`droppedByOverflow > 0`）就 `partial = true`，且不可逆**
——丢弃是不可逆的事实，不会因为后来写得好就假装库是完整的。

**D17-a — 容量淘汰的计数（一度写成偏差，现已闭合）**

`TLM-RET-05` 要求"超限按最旧优先淘汰**并计数**"。实现最初只给了布尔标记 `capacityTrimmed`，
没有条数——当时的理由是"给 `IStorageBackend` 加淘汰账本会污染它'只做追加'的定位"。
**后来发现这个理由不成立**：条数用**裁剪前后的 `approxRows()` 之差**就能算出来，
完全不需要后端配合记账。于是 `RetentionReport` 补上 `capacityEvictedRows`，
需求原文的"并计数"被直接满足，`ret05` 也从"断言可观测等价事实"升为硬断言。

| 想知道的 | 看哪里 |
|---|---|
| 本次是否因容量触发裁剪 | `RetentionReport::capacityTrimmed` |
| **本次淘汰了多少条** | `RetentionReport::capacityEvictedRows` |
| 本次时间清理删了多少条 | `RetentionReport::purgedRows`（**不含**容量淘汰，两者刻意分开） |
| 后端根本不支持容量裁剪 | `Status::capacityUnsupported`（且只记一次日志，不反复试） |

> **教训**：把"实现不了"写成文档偏差之前，先确认它**真的**实现不了。
> 这一条的"接口污染"顾虑是我想多了——用两个现成数字相减就够了。

**D17-b — `DropOldest` 在健康后端下不可达（实现比设计更保守，已写回文档）**

设计 §4.1 原文只写"缓冲满 → 淘汰最旧 + 计数"。实际实现是**先 `flushLocked()` 腾空间，再淘汰**，
于是：后端健在时 `DropOldest` 永不触发（**一条都不丢**），只有后端持续拒收时才真正丢弃。
这比原文更保守（是好事），但**必须写进文档**——否则使用者会以为 `DropOldest` 意味着"平时就在丢数据"。

## 10. 一句话

> **一条有界缓冲把高频写变成批量写，一个注入的后端把"存哪里"挡在模块外，**
> **一套 `[from, to)` 语义把查、回放、补发收成同一条路径，一个维护线程按策略清理并按序号如实暴露缺口。**
