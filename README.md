# telemetry-store · 实时数据留存层

> **实时数据存下来，让"刚才发生了什么"可以回答。**
>
> 它只回答一个问题：**"过去那段时间，这条流里到底发生了什么？"**
> —— 至于这条流是什么业务、谁需要看、画成什么样子，都不是它的事。

## 🎯 它解决什么问题

> 实时数据存下来，让"刚才发生了什么"可以回答。

### 为什么必须有

**没有它，实时系统就只是"看着动"：刷新一下全没了，出问题查不了，报告只能编。**

实时展示和留存是**两条路**，不是一条：

```
   实时事件流
        │
        ├──▶ 实时展示（不需要存储）
        │
        └──▶ ┌──────────────────┐
             │ telemetry-store  │
             │                  │
             │  写入 → 存储      │
             │  查询 → 区间取数  │
             │  回放 → 时间轴    │
             │  保留 → 过期清理  │
             └────────┬─────────┘
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
     轨迹回放      指标曲线      报告/追溯
```

**注意箭头是单向的**：留存层不回头依赖实时展示，也不认识那三个下游是谁。

### 它填的是链路里的第 ③ 节

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│   ①  入口     │   │   ②  管道     │   │   ③  留存     │   │   ④  出口     │
│  把设备数据   │──▶│  把事件推给   │──▶│  把数据存下来 │──▶│  把数据画出来 │
│  变标准       │   │  所有客户端   │   │  可查可回放   │   │              │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
  device-ingest      realtime-hub      telemetry-store       map-2d
                     + ws-client        ← 本仓
```

### 为什么"补发"这件事落在它头上

这是它和 `realtime-hub` 的分界线，也是最容易混的一点：

| 问题 | 谁来回答 |
|---|---|
| "现在有数据了，怎么同时送到每个人手上？" | `realtime-hub` |
| "**刚才我不在，那段时间丢了什么？**" | **`telemetry-store`** |
| "我能按人筛选推送吗？" | 都不管——在 hub 外面包一层 |

`realtime-hub` 是**哑的**：断开的人就错过了，**它不补发**。
客户端重连后要拿回断线期间的数据，只能**自己去查留存层**。

> **这是两个模块，别混在一起。** hub 管"在场的人"，留存层管"发生过的事"。

## ✅ 核心要求

| 项 | 要求 |
|---|---|
| 写入 | **高频写入不拖垮主库** |
| 查询 | 按**设备 ID + 时间区间**取数 |
| 回放 | 输出成**时间轴格式**，直接喂给回放组件 |
| **补发** | 客户端重连后，能查"我断的那段时间发生了什么"（这是 `realtime-hub` 明确不管的事） |
| 保留策略 | **可配置过期清理**，不然数据库只增不减 |
| **不认识业务** | 它只管"带时间戳的流式数据"，**不认识任何业务表** |

**一句话记法**：

```
   realtime-hub    =  "现在，通知所有在场的人"      → 管"在场"
   telemetry-store =  "刚才，到底发生了什么"        → 管"过去"
```

---

## ⚠️ 关键区分：这是数据层模块，不是"存业务数据的数据库"

**这一条搞混，整个模块就白拆了。**

```
   telemetry-store  →  设备位置、链路质量、指标曲线……（带时间戳的流）
   业务数据库        →  任务、方案、目标、编组……（业务实体）
```

| | `telemetry-store` | 业务数据库 |
|---|---|---|
| 存什么 | **带时间戳的流式数据** | 业务实体 |
| 数据形状 | 追加为主，几乎不改不删 | 增删改查都有 |
| 主键 | **设备 ID + 时间** | 业务主键 |
| 生命周期 | 有**保留期**，到期清理 | 长期保存 |
| 谁能用 | **任何有实时流的系统** | 只有你的项目 |

**判断捷径**：抽出来的东西里如果出现下面这些词，**那是业务，别进来**：

```
   任务   方案   目标   场景   阶段   编组   评估
```

真正的留存层里只有这些词：

```
   设备   数据   事件   时间   区间   保留
```

## 🚫 它明确不做

| 做 | 不做 |
|---|---|
| 追加写入高频流式数据 | **推送**——那是 `realtime-hub` 的事 |
| 按设备 ID + 时间区间查询 | **业务查询**——"哪个任务完成了"去问业务数据库 |
| 输出时间轴，供回放 / 曲线使用 | **画图**——那是出口模块（`map-2d` 等）的事 |
| 可配置的过期清理 | **业务规则判断**——它不认识告警、任务、编组 |
| 为断线客户端提供补发查询 | **连接管理**——谁连着、谁断了，它不知道也不关心 |

## 🔌 对外接口（草案 · 待冻结）

> **注意：这一节是草案，不是定稿。** 文档只冻结了它的**职责**，没有冻结接口形状。
> 按"先定接口、再写代码"的规矩，接口要在 R1 开工前定下来并冻结——**下面是讨论起点，不是承诺。**

**业务侧只认识这几个动作：**

```text
   append(deviceId, type, payload, ts)      写入一条流式数据（高频路径）
   query(deviceId, fromTs, toTs)            区间取数 → 按时间升序
   replay(fromTs, toTs [, deviceId])        回放 → 时间轴格式
   since(lastSeenTs [, deviceId])           补发 → "我断的那段时间发生了什么"
   purge(beforeTs)                          过期清理
```

**反向接口（宿主注入，模块不写死实现）：**

```text
   IStorageBackend     存哪里（内存 / SQLite / 时序库 / 文件分段）由宿主决定
   IRetentionPolicy    留多久、什么时候清，由宿主配置
   IClock              时间来源注入，便于测试与回放
```

**三条硬约束**（来自拆模块的四条规则）：

1. **依赖单向**——不 import `device-ingest` / `realtime-hub` / `map-2d` 的任何内部
2. **实现通过反向接口注入**——存储后端不是写死的，换库不改模块
3. **零业务词**——源码里搜不到"任务 / 方案 / 目标 / 场景 / 阶段 / 编组 / 评估"

### 实现选型（待定）

| 项 | 候选 | 取舍 |
|---|---|---|
| 存储后端 | 内存 / SQLite / 嵌入式时序库 / 文件分段 | **不预设**——由 `IStorageBackend` 注入；默认给一个零依赖实现，让 clone 下来就能跑 |
| 写入方式 | 直写 / 批量缓冲 | 目标是"高频写入不拖垮主库"，批量是主要手段 |
| 清理机制 | 定时任务 / 写入时顺带 / 分区丢弃 | 取决于后端选型 |

## 🔗 与其它模块的关系

```
   device-ingest ──ISink──▶ 宿主 ──▶ realtime-hub ──WebSocket──▶ ws-client ──▶ 宿主适配器 ──props──▶ map-2d
                             │                                                                    ▲
                             │ 落库                                                         回放数据 │
                             ▼                                                                    │
                      telemetry-store ────────────────────────────────────────────────────────────┘
```

**所有箭头都是单向的**，没有一个模块回头依赖另一个。这就是它们能被独立拿走的原因。

| 关系 | 说明 |
|---|---|
| 与 `realtime-hub` | **互不认识**。hub 推给在场的人，留存层记下发生的事；两者之间由**宿主**装配 |
| 与 `device-ingest` | **不认识**。设备接入只管把报文变标准数据，落不落库由宿主决定 |
| 与 `map-2d` | **不认识**。留存层输出时间轴，画成什么样是出口的事 |
| 与宿主的连接点 | 宿主里那几个**适配器文件**：`onEvent → append`、`重连 → since`、`replay → 喂给出口` |

### 为什么单独一个仓

| 做法 | 评价 |
|---|---|
| **独立仓**（本仓） | 它是**数据层**，和"推"是两件事；任何人只要有实时流就能用 |
| 并入 `realtime-hub` 仓的第三个包 | 也合理——它写的是"实时流"，和 hub 挨着说得通；但会让 hub 仓从"一条通道"变成"通道 + 存储" |

**两条路都成立，本仓选了独立仓。** 理由是：**留存层能被单独拿走的价值，比两个模块挨着省下的一个仓更大**——
"把实时流存下来，能查能回放"这件事，和 WebSocket 一点关系都没有。
